# Unit 2 Analysis

## Type mapping (Step 3)

| Table | Column | Unit 1 | PostgreSQL type | Reason |
|---|---|---|---|---|
| players | player_id | int, PK | `INTEGER GENERATED ALWAYS AS IDENTITY` | Surrogate key generated by the database |
| players | player_name | varchar | `VARCHAR(32)` | Short display name; 32 characters is enough for a nickname |
| players | referred_by | *(new)* | `INTEGER NULL` | Self-referencing FK to `players(player_id)`; NULL means the player was not referred |
| game_modes | mode_id | int, PK | `INTEGER GENERATED ALWAYS AS IDENTITY` | Surrogate key generated by the database |
| game_modes | mode_name | varchar | `VARCHAR(50)` | Short catalog label (e.g., "Ranked", "Double Up") |
| matches | match_id | int, PK | `INTEGER GENERATED ALWAYS AS IDENTITY` | Surrogate key generated by the database |
| matches | match_name | varchar | `VARCHAR(100)` | Short human-readable label, slightly longer than a nickname |
| matches | is_active | bool | `BOOLEAN` | Flag |
| matches | duration_seconds | int | `INTEGER` (nullable) | Duration; the unit is in the column name; NULL while the match is active |
| match_participants | player_id | int, PK, FK | `INTEGER` | FK must match the type of `players.player_id` |
| match_participants | match_id | int, PK, FK | `INTEGER` | FK must match the type of `matches.match_id` |
| match_participants | joined_at | timestamp | `TIMESTAMP` | Point in time |
| match_participants | score | int | `INTEGER` | Whole-number points (LP), see below |
| match_modes | match_id | int, PK, FK | `INTEGER` | FK must match the type of `matches.match_id` |
| match_modes | mode_id | int, PK, FK | `INTEGER` | FK must match the type of `game_modes.mode_id` |

### Key decisions

- **I kept `score` as `INTEGER`, not `NUMERIC(3,2)`.** On this platform the score is a whole number of points (in the future, TFT League Points), not a fractional rating, so a decimal type would add precision that never exists in the data.
- **`score` may be negative, so `CHECK (score >= 0)` is not needed.** A player can lose LP after a defeat, and a lower bound of 0 would reject valid data.
- **`VARCHAR` lengths 32 / 50 / 100.** Each length is sized to its data instead of a default of 255: player nicknames are short (32), mode names are short catalog labels (50), and match names are descriptive labels that may be a little longer (100).
- **`match_name` stays** as a human-readable label for a match. It was part of the Unit 1 schema, and removing it would bring no benefit.
- **`players.referred_by` is new** (change from Unit 1). It is a nullable self-referencing foreign key that records which player referred another player.

## Constraints table (ON DELETE)

I chose the deletion behavior of each foreign key based on whether the child rows still have meaning without their parent.

| Foreign key | ON DELETE | Reason |
|---|---|---|
| `players.referred_by` → `players(player_id)` (`fk_players_referred_by`) | `SET NULL` | The referred player's own account and history must survive when the referrer leaves; only the referral link is lost. |
| `match_participants.player_id` → `players(player_id)` (`fk_match_participants_player`) | `RESTRICT` | Participation rows are historical telemetry and must not disappear silently when someone tries to delete a player. |
| `match_participants.match_id` → `matches(match_id)` (`fk_match_participants_match`) | `CASCADE` | A participation row describes one specific match and has no meaning once that match is gone. |
| `match_modes.match_id` → `matches(match_id)` (`fk_match_modes_match`) | `CASCADE` | A match-mode assignment only describes its match, so it should be removed together with the match. |
| `match_modes.mode_id` → `game_modes(mode_id)` (`fk_match_modes_mode`) | `RESTRICT` | A mode used by recorded matches is part of their history and must not be deleted from under them. |

**Deleting a referrer (`SET NULL`).** This rule governs the case where a player who invited others deletes their account or is removed by an administrator. It affects every player whose `referred_by` points to that account. With `SET NULL`, those players keep their accounts and match history, and only the information "who invited me" is cleared. With `CASCADE`, deleting one referrer would delete every player they invited, and then everyone those players invited, which could wipe out a whole chain of real accounts. With `RESTRICT`, a player could never delete their account as long as anyone they once invited still exists.

**Deleting a player (`RESTRICT`, unchanged from Unit 1).** This rule governs an attempt to delete a player who has already played matches. It affects that player's rows in `match_participants`, and indirectly every statistic computed over those matches (rankings, average scores, match results). With `RESTRICT`, the delete is refused while participation rows exist, so history can only be removed on purpose. With `CASCADE`, one delete would silently remove the player's results from every match, and the remaining match records would show fewer participants than really played.

**Deleting a match (`CASCADE` on `match_participants` and `match_modes`, unchanged from Unit 1).** This rule governs removing a match, for example a test match or a match that was recorded by mistake. It affects all participation rows and all mode assignments of that match. With `CASCADE`, the match and everything that only describes it is removed in one step. With `RESTRICT`, an administrator would first have to delete every participant and mode row by hand, and forgetting one would block the delete. With `SET NULL`, the rows would be left without a match, which is impossible here anyway because `match_id` is part of the primary key and cannot be NULL.

**Deleting a game mode (`RESTRICT`, unchanged from Unit 1).** This rule governs removing a mode from the catalog, for example when a mode is retired from the game. It affects every match that was played in that mode. With `RESTRICT`, a mode that appears in history cannot be deleted, so old matches still show which mode they used. With `CASCADE`, deleting the mode would remove its rows from `match_modes`, and old matches would lose their mode information without any error.

## CHECK constraints

I moved the rules that Unit 1 only described in prose into the schema, so the database rejects invalid rows instead of relying on application code.

| Constraint | Table | Invalid state it makes impossible |
|---|---|---|
| `chk_players_no_self_referral` | `players` | A player listed as their own referrer |
| `chk_matches_duration_non_negative` | `matches` | A match with a negative duration |
| `chk_matches_active_no_duration` | `matches` | An active match that already has a final duration |
| `chk_matches_inactive_with_duration` | `matches` | A finished match without a duration |
| `uq_game_modes_mode_name` (UNIQUE) | `game_modes` | Two catalog entries with the same mode name |

**`chk_players_no_self_referral`** makes it impossible for `referred_by` to equal the player's own `player_id`. Such a row could appear through a bug in the sign-up flow (for example, filling the referrer field from the current player's own session) or through a manual update. A self-referral is meaningless and would also break referral reports, such as counting how many people each player invited. The check uses `IS DISTINCT FROM` instead of `<>` so that a NULL `referred_by` (no referrer) is still allowed.

**`chk_matches_duration_non_negative`** rejects a negative `duration_seconds`. A negative value could come from a clock problem, for example when the end time is computed before the start time or the two timestamps are swapped. A negative duration would also make averages such as "average match length" wrong.

**`chk_matches_active_no_duration` and `chk_matches_inactive_with_duration`** together tie `is_active` and `duration_seconds`: an active match has no duration yet, and a finished match must have one. Without them, the application could finish a match and forget to store its duration, or store a duration and forget to clear the `is_active` flag. Both cases leave the match in a contradictory state, and queries that use one column to decide about the other (for example, "finished matches" vs. "matches with a duration") would return different results. Because a new match is active by default (`DEFAULT TRUE`), a match can be created without a duration and closed later with one `UPDATE` that sets both columns.

**`uq_game_modes_mode_name`** is not a CHECK, but it belongs here because it guards the catalog in the same way. Without it, the same mode (for example "Ranked") could be inserted twice, for example by running a seed script a second time. Matches would then be split between two IDs for the same mode, and any statistics grouped by mode would be wrong.

## Changes from Unit 1

- **New column `players.referred_by`.** A nullable, self-referencing foreign key to `players(player_id)` records which player invited another player. I placed it on `players` because a referral is a fact about a single player: each player has at most one referrer, so the relationship is one-to-many from referrer to referred players, and the "many" side holds the foreign key. A separate `referrals` table would only be needed if a player could have several referrers or if the referral itself carried extra attributes (such as a date or a reward), which is not the case on this platform. The column is nullable because most players join without a referral, and it uses `ON DELETE SET NULL` (see above).
- **Generated surrogate keys.** `player_id`, `mode_id` and `match_id` are now `INTEGER GENERATED ALWAYS AS IDENTITY`, so the database assigns them and the application cannot insert a conflicting or made-up ID.
- **Sized text types.** The generic `varchar` from Unit 1 became `VARCHAR(32)`, `VARCHAR(50)` and `VARCHAR(100)`, sized to each value (see Type mapping).
- **New CHECK constraints on `matches`.** The link between `is_active` and `duration_seconds` was only described in prose in Unit 1. Now it is enforced by `chk_matches_active_no_duration` and `chk_matches_inactive_with_duration`, and `is_active` defaults to `TRUE`.
- **Self-referral check.** `chk_players_no_self_referral` comes together with `referred_by`.
- **Unique mode names.** `uq_game_modes_mode_name` ensures that the game-mode catalog cannot contain duplicates.
- **Named constraints.** Every constraint has an explicit name with a `pk_`, `fk_`, `chk_` or `uq_` prefix, so error messages point directly to the rule that failed.
- **ERD update.** In the Unit 1 ERD image, `player_id` and `match_id` in `MATCH_PARTICIPANTS` were marked only as FK, although the schema definition makes them a composite primary key. The updated diagram marks them as PK, FK and adds `referred_by` to `PLAYERS` with its self-relationship (zero-or-one referrer to zero-or-many referred players).
